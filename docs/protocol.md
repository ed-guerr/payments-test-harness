# Wire protocol

The three backend processes speak a compact TCP protocol. The harness's
`harness/src/protocol/registry.json` is **generated from the C binaries**
(`npm run gen:registry` runs each binary with `--introspect`), so the tables
below never drift from the code — the code is the source of truth.

## Frame format

Every message is one frame:

```
offset  size  field         value
------  ----  ------------  -----------------------------
0       2     magic         0x5046 ("PF"), little-endian
2       2     msg_id        message id (table below), little-endian
4       4     payload_len   length of payload, little-endian, ≤ 2048
8       n     payload       packed message body (n = payload_len)
```

- Endianness: **little-endian** throughout.
- The header is exactly **8 bytes**.
- Payloads are **packed structs** (`PF_PACKED` / `__attribute__((packed))`):
  `sizeof(struct) == sum of field sizes`, no alignment padding. Field offsets
  in the tables below are the real `offsetof` values.
- `char[N]` fields are NUL-padded to N bytes.
- A client may send one frame and read one response; connections stay open
  (the server closes only on protocol errors or client disconnect).

### Ack status codes (per ack type)

| Ack | code | meaning |
|---|---|---|
| `PaymentAck` | 0 / 1 / 2 / 3 | ok / account_not_found / duplicate_txn / invalid |
| `TransferAck` | 0 / 1 / 2 / 3 / 4 | ok / insufficient_funds / no_account / self_transfer / no_entry |
| `SettleAck` | 0 / 1 / 2 | ok / not_complete / already_settled |

(Business rejections are returned as a normal ack with a non-zero status —
`ErrorAck` is reserved for protocol/transport failures and handler errors.)

## ErrorAck

Every process can answer any message with `ErrorAck` (255) when the frame is
structurally bad or a handler fails:

| code | meaning |
|---|---|
| 1 | unknown message id (not in the dispatch table) |
| 2 | bad magic |
| 3 | oversized payload (payload_len > 2048) |
| 4 | payload size mismatch (len ≠ sizeof(struct)) |
| 5 | handler returned non-zero (internal error, e.g. db failure) |

## How the registry is generated (callout)

Each message is defined once in C as an **X-macro field list**
(`include/pay/messages.h`), which expands into both the packed struct *and*
the metadata table (name, type, `offsetof`). `--introspect` prints that table
as JSON. The harness consumes the JSON to build:

- the TypeScript codec (pack/unpack at exact offsets),
- the GUI's Protocol Registry tab,
- the MCP `get_message_schema` tool (with KB notes),
- suite validation (unknown message/field → descriptive error + KB hints).

One definition, four consumers. Change a message in C → `make` →
`npm run gen:registry` → the diff of `registry.json` is your review surface.
